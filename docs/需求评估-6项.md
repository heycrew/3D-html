  推荐实施顺序：1 → 2 → 3 → 4 → 5 → 6
  工作量合计约 4.7 天（不含真机验证与返工）

=====================================================================
【1】桌面背景默认纯黑色
=====================================================================
  理解：把「桌面背景」参数的默认值由 #2a2118（深棕）改成 #000000。

  方案：build/js/01-schema.js 里 bookBg 的 def 改掉（一行）。

  注意：默认值只影响**新工程**；已经保存在浏览器里的工程（IndexedDB）会保留当时的旧值，
  用户仍需在面板里手动改一次。建议同时在使用说明里写一句。

  工作量：0.1 天。风险：几乎没有。


=====================================================================
【2】点击页码可输入数字，直接跳转到对应页码
=====================================================================
  理解：产物底部那条页码导航（现在是「2 / 12」纯文本）点一下能输入数字，回车跳到那一页。

  方案：
    · 页码元素从 <span> 改成可编辑：点击 → 变成 <input type="number">（或 contenteditable）
      → 回车/失焦 → 校验范围 → fb.goTo(n-1, { instant: false })，它本身已带动画
    · 手机上点开要能唤起数字键盘（inputmode="numeric"）✔
    · 翻页过程中要屏蔽（沿用现有 busy 标志）
    · 顺手把「点页码跳转」的提示与第 4 项的引导页文案呼应（那里写着「点击页码可跳转指定页面」）

  改动点：build/js/12-bookpage.js（buildCss 加输入态样式、buildBody 的 navText、buildInit 的事件）。

  风险/细节：
    · 输入框宽度要自适应（1 / 12 与 100 / 120 宽度不同）
    · 键盘回车在不同输入法下的表现（用 keydown 判 Enter + blur 兜底）
    · 与「点页面开 360」的手势不能互相误触（页码在导航条里，已 z-index 70 浮在书上）

  工作量：0.5 天。


=====================================================================
【3】示意区底部新增自定义文案
=====================================================================
  理解：在四角示意框的底部加一行说明文字，默认「点击查看360全景图」；
        颜色/描边风格与四角一致（同样要保证任何底图上都看得清）。

  方案：
    · 新增参数：文案内容（默认「点击查看360全景图」）；可选字号
    · DOM：示意框容器里加一个 <div class="hint-cap">，与四角共用那套「浅色文字 + 深色描边」
      （用同样的 filter: drop-shadow 双层描边；角是 border，文字用 text-shadow 等价实现）
    · 与第 4 项的「加载页底部文案」是**同一份文案参数**，样式复用同一个类

  「位置齐平底部四角横线的底部」有两种合理解读（需拍板）：
    ① 文案在框**内**、贴着底边（文字底边与底部两角的横线重合）
    ② 文案在框**外**下方，文字底边与框底边对齐（等于压在框线上）
  实现上 ① 更常见（引导语含在框里），② 会让文字压住角的横线。默认按 ① 做，改起来只是偏移量。

  工作量：0.3 天。


=====================================================================
【4】加载页升级为「操作引导页」（最大的一块）
=====================================================================
  理解：现在的加载页只有一行文案 + 进度。要升级成一张引导页，包含：

    ┌──────────────────────────────┐
    │  点击页码可跳转指定页面          │  ← ① 顶部说明（可自定义，见【5】）
    │                              │
    │        ┌────────────┐        │  ← ② 模拟四角示意区（居中，静态展示）
    │        │   360 icon  │        │     中间放一个 360 全景图标
    │        └────────────┘        │
    │        点击查看360全景图        │  ← ③ 底部文案（与四角框底边齐平，同【3】的样式）
    │                              │
    │            1 / 12            │  ← ④ 模拟页码标识（静态样式，不可点）
    └──────────────────────────────┘
      另：左上/某处仍显示加载文案与「已加载 x / y 页」

  方案要点：
    · 时长：`max(实际加载耗时, 3000ms)` —— 实际耗时本来就在量（现在的最短 350ms 改为 3000ms）
    · 「按实际加载速度计算」= 用真实预检进度驱动；若还在加载就继续显示引导页
    · 模拟元素全部 pointer-events:none（不可交互），只是"预告"真实界面长什么样
    · 360 图标：内联 SVG（不引外部资源，保证离线可用、体积零增加）
    · 布局用与产物一致的居中容器，颜色沿用 bookBg / 纸色，保证与真实页面观感连贯
    · 第 3 项的底部文案与第 4 项的底部文案共用参数与样式类

  工作量：1.5 天（布局 0.5 + 逻辑 0.3 + 图标与样式复用 0.4 + 自测 0.3）
  风险：
    · 「至少 3 秒」会让素材少的用户觉得慢 —— 建议做成参数（默认 3 秒，可调 0~10 秒）
    · 引导页与真实页面的视觉衔接（淡出时不要闪）—— 沿用现有的淡出 + 最短时长机制

=====================================================================
  理解有两种，需拍板（见文末）：

=====================================================================
【6】把工作台封装成绿色版桌面应用
=====================================================================
  三条路线对比（按本机可构建性排列）：

  ★ 推荐：C# + WebView2 单文件窗口应用
      形态：一个真正的窗口程序（无浏览器地址栏、有图标与标题），内部起本地 HTTP 服务、
            WebView2 导航到 http://127.0.0.1:port/studio.html。
      体积：自包含发布约 12~20MB（不依赖用户装 .NET）；框架依赖版约 1MB（需 .NET 8 运行时）
      绿色度：拷目录即用 ✔（自包含）；依赖系统 WebView2 运行时（Win11 自带、Win10 1803+
              一般随 Edge 自带，可在启动时检测并给出下载提示）
      本机可行：✔（dotnet 8 SDK 有、WebView2 运行时已装、NuGet 可联网取包）
      工作量：2 天（HTTP 静态服务 ~150 行 C# + 窗口宿主 + 单实例 + 端口占用处理 + 图标 +
              发布脚本 + 在无 .NET 的机器上验证一次）

  ○ 备选：Electron
      形态：真窗口 ✔；体积 ~150~200MB（含 Chromium）
      本机可行：✔（npm 可装 electron + electron-builder）
      优点：最省心、生态成熟、跨平台（将来要 macOS 直接能出）
      缺点：体积是前者的 10 倍以上；"绿色版"拷起来沉
      工作量：1 天

  ✗ 不推荐（本机）：Tauri
      体积最小（~5MB 级）、依赖系统 WebView2
      但本机缺 MSVC 与 mingw → 必须先装 VS Build Tools（~1~2GB）或 mingw-w64，属于
      "为了打这个包先装一整套工具链"，性价比低（除非以后还要频繁出 Rust 桌面端）

  △ 最低成本：把现在的 启动工作台.bat 换成一个小 exe（dotnet 单文件，~1MB）
      作用：起本地服务 + 打开系统默认浏览器 + 托盘退出。
      优点：1 小时内可完成、体积极小、零依赖
      缺点：**仍然是浏览器窗口**，不是"桌面应用"；如果这点可接受，它是性价比最高的过渡方案

  工作量：2 天（推荐路线）。风险：
    · 无 WebView2 的机器要兜底提示（可在 exe 里检测注册表 pv 值）
    · 端口占用（沿用 8788，被占则顺延）
    · 单实例（避免重复双击起多个服务）
    · 打包后 studio.html 与 lib/ 的路径（内嵌资源 or 随目录发布）—— 建议**随目录发布**，
      这样用户仍然能直接替换 lib/ 里的库与音效（比内嵌更符合我们现在的发布习惯）

=====================================================================
决策（2026-09-17 已定）
=====================================================================
  A.【5】"手机端页面顶部的文案" = **产物网页的标题**（即 <title>，手机打开链接时顶部/微信
     分享栏显示的那行）。当前固定是 "360° 产品展示"（08-app.js 里的 STATE.title 默认值），
     工作台**没有**改它的入口 —— 所以这项要做的是：给工作台加一个「页面标题」输入。
     代码位置：05-codegen.js:180 与 12-bookpage.js:937 都是 `state.title || '360° 产品展示'`
     / `'电子图录'`，输入框写 STATE.title 即可，两处自动生效。

  B.【3】【4】"齐平底部四角横线的底部" = **文案在框内、贴着底边**（文字底边与底部两角的
     横线重合）。样式与四角一致：浅色文字 + 深色描边（保证任何底图上都看得清）。

  C.【6】桌面应用必须先满足「**在其他 Win10 / Win11 机器上都能用**」这条硬要求：
     · **Electron**（~180MB）：自带 Chromium，零前提，任何 Win10/11 都能跑 —— **满足硬要求的最稳选择**
     · C# + WebView2（~15MB）：体积小、真窗口，但要依赖机器上已有 WebView2 运行时
       （Win11 自带；Win10 1803+ 多数随 Edge 自动装了，但**不保证**）→ 需内置检测 + 引导安装
     · 最小 exe 启动器（~1MB）：兼容性最好（只要系统有浏览器），但仍是浏览器窗口
     · Tauri：本机缺 MSVC/mingw，要先装 VS Build Tools ~1~2GB

     结论：**默认走 Electron**（兼容性是硬要求，体积换可靠）；若后续确认目标机器都带
     WebView2 运行时，可换成 C# + WebView2 把体积压到 15MB。

  另外补充两条实现口径（评估时提到的风险，按此执行）：
    · 【4】的"至少停留 3 秒"做成参数：bookLoadMinMs（默认 3000，可 0~10000），
      实际时长 = max(真实加载耗时, bookLoadMinMs)
    · 【6】把 studio.html 与 lib/ **随目录发布**（不内嵌进 exe），这样用户仍能直接替换
      lib/ 下的库与音效，和现在的发布习惯一致
