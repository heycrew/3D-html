# 批量导入图 —— 设计文档

> 状态：待 review
> 目标读者：实现者（下一份「实现计划」的输入）

## 1. 背景

工作台（`studio.html`，本地服务版与 Electron 桌面版）目前的书页素材只能**一张一张传**：
封面、封底、每张内容页的「本页图」、以及每页自己的 360 素材组，都要在左栏「书页」里
分别点按钮、分别选文件。

真实场景：`D:\北京丰讯\北京丰讯-小茶书产品\线上线下同步拍\秋拍图录` 一次就有
**158 个内容页、702 张页图 + 2 张封面封底 = 704 张**。手工点 704 次不可行。

## 2. 需求与已确认的规则

### 2.1 原始需求

1. 选一个路径（自定义），把该路径下名字为「封面」的图片传成封面、「封底」传成封底。
2. 把该路径下所有子文件夹名当作内容页页码（不含封面封底）——如子文件夹叫 `1`
   就是内容页第 1 页；再把子文件夹里名字为 `0` 的图传成该页的「本页图片」，
   其余的 `1`、`2`… 按顺序传成该页的 360 素材图。

### 2.2 澄清后确定的规则（已逐条拍板）

| 决策点 | 结论 |
|---|---|
| 识别规则 | **A**：子文件夹名必须纯数字；非数字目录忽略并列出；页码缺口**保留空页**；没有 `0.*` 时该页本页图**留空** |
| 与已有数据的关系 | **清空重建**：整本书按这棵目录树重新生成，旧的封面/封底/内容页全部替换 |
| 上传交互 | 选完目录先弹**识别结果预览**，用户点「开始导入」才上传 |
| 取目录方式 | **方案 1**：Chromium 自带 `<input type="file" webkitdirectory>`，纯前端、两端通吃 |
| 预览图格式 | **按原文件类型**：原 JPEG → 降采样存 JPEG；原 PNG → 存 PNG |
| 页码保护 | **不设硬上限**；页数 > 300 时在预览里高亮并要**二次确认** |

**「清空重建」的范围**：封面、封底、内容页，**以及窑口图录条目**（见 §2.3）。
**`logo` 保持不动** —— 它不属于这棵目录树。

### 2.3 窑口图录的自动重建（2026-09-30 追加的需求）

批量导入时，把**没有 360 素材**的内容页按页码顺序**重建**进窑口图录：

- **清空重建，不追加**：导入后窑口图录 = 全部「没有 360 素材」的页；手工配过的条目会被替换。
  用户明确同意推翻原先「窑口图录条目保持不动」的说法。
- **只在批量导入时做**：不加开关，也不在别处触发。
- **标题写页码**（`第 N 页`）；`page` 用**产物页码**：内容页第 N 页 → `page = N + 1`（1 是封面）。
  目录树里只有数字文件夹名，没有窑口名称这类文字，所以标题只能是页码。
- **自定义图留空** → 产物里回退用该页自己的图（既有行为）。
- 判定「没有 360 素材」= 该页 `items` 里**未被 `off` 屏蔽**的条目数为 0。
- ⚠️ 已知边界：若某个图录**所有页都有 360 素材**，重建出来就是空的，而产物在窑口图录为空时
  会**回退显示「全部页面」的图墙**（`12-bookpage.js:1007`，老工程行为不变）。
  导入预览里会提示这一点。

## 3. 真实目录结构与识别结果

以 `秋拍图录` 为例（已实测）：

```
秋拍图录/
  封面.jpg                    → 封面
  封底.jpg                    → 封底
  .DS_Store                   → 忽略（macOS 垃圾）
  ._.DS_Store                 → 忽略
  ._4-                        → 忽略
  1/
    0.jpg                     → 第 1 页的本页图
    1.JPG  2.JPG  3.JPG       → 第 1 页的 360 帧（按数字排序）
  2/
    0.jpg                     → 只有本页图、没有 360 素材（合法，共 19 页这样）
  ...
  158/
    0.jpg  1.JPG … 9.JPG
```

实测统计（158 页）：纯数字目录 158/158、页码 1~158 连续无缺口无重复、
每页都有 `0.*`、帧名全是纯数字、没有更深层子目录。

## 4. 识别器规格

### 4.1 接口

新增模块 `build/js/09-dirimport.js` → `SD.DirImport.scan(entries)`。

- **纯函数**：不碰 DOM、不碰 `SD.STATE`、不发网络请求。这样可以在探针里直接喂假数据断言。
- 输入 `entries`：`[{ path: '秋拍图录/1/0.jpg', file: File }]`
  （`path` 取自 `File.webkitRelativePath`；调用方负责配对）

### 4.2 输出

```js
{
  root: '秋拍图录',              // 选中的目录名（会被剥掉，不参与识别）
  /* scan 不读图，所以这里没有 w/h —— 尺寸由上传阶段（Materials.upload）补上 */
  cover: { name, file, path } | null,
  back:  { name, file, path } | null,
  pages: [                       // 按 no 升序；缺口处这条也在，只是内容为空
    { no: 1, pageImg: {…}|null, frames: [ {…}, … ] }
  ],
  total: { pages: 158, images: 704 },   // images = 需要上传的张数
  skipped: { system: 3, other: 0 },     // 被忽略的系统文件 / 其它认不出的文件
  warnings: [ { code, text } ]          // 见 4.4
}
```

### 4.3 识别规则（按优先级）

| 输入形态（剥掉 `root` 之后） | 归到 | 备注 |
|---|---|---|
| 以 `.` 开头的文件或目录 | **忽略**（计入 `skipped.system`） | 必须显式过滤：`._0.jpg` 的扩展名是 `.jpg`，不过滤会被当成图片 |
| 根目录下，去扩展名后恰好等于 `封面` / `封底`（去首尾空格） | 封面 / 封底 | 扩展名大小写不敏感；多张时取第一张 + 告警 |
| `<纯数字>/0.<ext>` | 第 N 页 `pageImg` | `0` 也要求大小写/空格不敏感 |
| `<纯数字>/<其它图片>` | 第 N 页 `frames` | 按 `naturalCompare` 排序 |
| `<纯数字>` 目录里没有 `0.<ext>` | `pageImg: null` | 留空，计入 `warnings` |
| 非纯数字的一级子目录 | 忽略，列进 `warnings` | |
| 更深的子目录 | 忽略，列进 `warnings` | |
| 根目录下其它文件、非图片文件 | 忽略（计入 `skipped.other`） | |

### 4.4 排序与告警

- **帧序**：`SD.Materials.naturalCompare(a, b)` —— 把 `03-materials.js` 里
  `importFiles` 用的那句 `localeCompare(..., {numeric:true, sensitivity:'base'})`
  提成公开函数，识别器和上传共用**同一处**规则，避免两套排序漂移。
  这条必须有断言：**帧序错一格，整个 360 旋转就错乱**。
- `warnings` 的 `code`：`no-cover` / `no-back` / `multi-cover` / `multi-back` /
  `no-pages` / `non-numeric-dir` / `page-without-image` / `nested-dir` /
  `too-many-pages`（pages > 300）/ `duplicate-frame`（同页重名帧）

## 6. 数据流

1. 点「批量导入（选文件夹）」→ `pickDirectory()` 弹系统目录框
   → 得到 `File[]`，各自配 `webkitRelativePath`
2. `SD.DirImport.scan(entries)` → 弹**识别结果预览**
3. 用户点「开始导入」→ 按 **封面 → 封底 → 第 1 页本页图 → 第 1 页帧 → 第 2 页 …**
   串行上传，复用 `SD.Materials.importFiles`（本身就是串行 + 降采样 + POST `/@upload`）
4. 全部完成后**一次性**重建 `STATE.book`：`cover` / `back` / `pages`（含 `items`）、
   按封面图 `naturalWidth/Height` 校准 `w`/`h`、`active = 0`
5. `SD.Book.render()` + `SD.refresh()` + 一次 `SD.Store.autoSave()` + toast 汇总

### 6.1 两条锁死的约束（针对 704 张这个规模）

1. **导入过程中绝不触发自动保存。** `SD.Store.autoSave()` 是**全量快照**，
   704 张若每张触发一次，会反复序列化 158 页结构（其中含 704 个 File），把工作台拖死。
2. **上传全部成功后才改 `STATE.book`。** 中途取消或失败时，工作台保持原样，
   不会出现「清了半本」。已上传的图会被丢弃（本地服务里成为垃圾，见 §11）。

## 7. 界面

- **按钮**：书页版块，与现有 `btnUpCover` / `btnUpBack` 同排，按钮文案
  「批量导入（选文件夹）」。
- **识别结果预览模态**（复用工作台现有模态样式）：
  - 概览一行：`识别到 158 页 / 704 张图（另有 3 个系统文件已跳过）`
  - 封面 ✓/✗、封底 ✓/✗
  - 每页一行摘要：`第 1 页  本页图 0.jpg + 3 张素材` ／ `第 2 页  只有本页图` ／
    `第 3 页  缺本页图 + 4 张素材`
  - 告警清单（非数字目录、嵌套目录等）
  - 页数 > 300 时：概览高亮，按钮变「确认导入 158 页」（二次确认）
  - 按钮：**开始导入** / 取消
- **进度**：`正在上传 137 / 704 · 2.JPG`，带取消按钮；完成后 toast 汇总
  `已导入 158 页 / 704 张图`（有失败则列出失败清单）。

## 8. 错误处理

| 情况 | 行为 |
|---|---|
| 一个内容页都没识别到 | **拒绝**，不进入上传 |
| 没找到封面 / 封底 | 告警，允许继续（该项置空） |
| 没有本地服务（`SD.Materials.ping()` 失败，或 `isFileMode()`） | 沿用现有做法：`toast('err', '预览不可用', '请改用「启动工作台.bat」打开工作台')` 并中止（现有实现在 `08-app.js:368` / `391`） |
| 选错层级（例如选中了上一层的 `线上线下同步拍`） | 子目录名会是 `秋拍图录`（非纯数字）→ 命中 `no-pages` 被拒绝，提示「请选到以数字文件夹为直接子级的目录」 |
| 单张上传失败 | 计入失败清单，继续传其余；结束时汇总；**失败的不写进 state** |
| 用户取消 | 停止后续批次，丢弃结果，工作台不变 |
| 页数 > 300 | 预览里二次确认 |

## 9. 性能（实测数据，非估算）

用 `build/.verify/probe_preview_size.py` 对真实素材抽样 12 张测得：

| 方案 | 平均/张 | 704 张合计 |
|---|---|---|
| 现状 `960 PNG` | 462 KB | **317 MB** |
| 按原类型（本设计，素材全 JPEG） | 59 KB | **41 MB** |
| 改 JPEG + 边长 720 | 35 KB | 24 MB |

- 原图统一 `2000×2695`（正好 3:4，与书的默认 `900×1200` 同比例 → 封面校准后不留白），
  平均 268 KB。改动后**预览素材内存从 317 MB 降到 41 MB**，这是必须改的原因。
- 预期耗时 **1.5~3 分钟**（串行；每张要先从 540 万像素解码，再降采样，再 POST）。
- 本地服务的素材是全量留在内存里的（`/@mat` 无回收接口），所以必须控制单张体积。

4. **产物加载性能（§12 的验收标准）**：`build/.verify/probe_perf_boot.py` ——

## 11. 已知限制

1. **空文件夹看不见** —— 浏览器不返回空目录，"预先占一页空位"只能靠「＋添加页」。
2. **不能记住上次选的路径**（选了方案 1 的代价）。
3. 点「选目录」后 Chromium 会先遍历整棵子树，几千张图时会有短暂停顿。
4. 取消 / 失败时丢弃的素材会留在本地服务内存里直到它重启 —— `/@mat` 目前只有"全清"
   接口，没法精准回收。
5. 刷新页面能靠 IndexedDB 恢复（存的是原始 File），但恢复时要**重新上传一遍** 704 张，
   同样要等 1.5~3 分钟。
6. 跳到远处、尚未预取过的页，首次仍要现场加载（线上 CDN 约 0.2~1 秒，弱网更久）——
   §12.4 的跳转预取把这段等待压到最低，但不可能为零。

## 12. 产物加载性能（长图录首屏与跳转）

> 这一节和「批量导入」不是同一件事：修的是**产物打开时的加载策略**，
> 对现有任何长图录（哪怕 40 页）同样生效。之所以放进这份设计一起做，
> 是因为批量导入会把图录从几页直接推到 158 页 —— 不修的话新功能一上线就是灾难。

### 12.1 实测（158 页真实素材，20 Mbps 下行 / 40 ms 延迟）

探针 `build/.verify/probe_perf_boot.py`（自造 158 页产物 + CDP 限速）：

| | A 现状 | B 只放行前 3 页 |
|---|---|---|
| 打开到能看见书 | **24.3 秒** | **1.2 秒** |
| 下载总量 | **58.6 MB** | 3.2 MB |
| 请求的 book/ 图 | **163 张** | 8 张 |

按 4G 弱网（8 Mbps）换算，现状接近一分钟白屏。

### 12.2 根因：库本身是对的，是我们把它挡住了

`vysmo-flipbook` 在 `lazy: true` 时**只加载「当前页 ± preloadWindow」就 ready**：

```js
let Y = R ? X(c).then(...)           // lazy：只等 c±k 这几页
           : it(n.pages).then(...)   // 非 lazy：Promise.all 全量加载
async function ae(...){ R && await X(h); ... }   // 翻页也只等这一小窗口
```

坏在 `12-bookpage.js` 的 `bootFlip()`（2127-2145）自己又干了一遍全量预检
（`PAGES.forEach(pg => { new Image().src = pg.src })`），并让 `initFlip()`
等到**所有页 decode 完**（`left === 0`）才调用。

代码里给的注释理由是「翻页库要等所有页 decode 完才会 ready，坏图会让它一直等下去」——
**这个理由在 `lazy: true` 下不成立**，应该是 `lazy: false` 时代的经验，
配置改了之后没跟着修，于是这段预检一直在白白拖住首屏。

### 12.3 顺带修掉的现存 bug

```js
PAGES = keep.filter(function (x) { return !!x; });   // bootFlip 里
```

预检失败的页会被**从页表里删掉**，后面所有页整体前移 —— 158 页里坏 1 页，
第 5 页的图就会显示在第 4 页上，页码和图错位。正确做法是**保留槽位、换成占位图**。

### 12.4 必做的 5 项

| # | 改动 | 说明 |
|---|---|---|
| 1 | 预检收窄到首屏 | 只探测「当前页 ± `bookPreload` + 1」这几页（约 5 页），其余交给库的懒加载 |
| 2 | 跳转前预取目标页 + loading 反馈 | 见 12.5。窑口图录 / 进度条跳转时先灌目标页，再 `fb.goTo` |
| 3 | 拖进度条时就预取 | `seekRange` 的 `input` 里节流预取当前指向的页，松手即跳 |
| 4 | 缺图页补占位图 + 不再剔页 | 修 12.3 的页码错位；同时从源头消灭坏图 |
| 5 | `fb.goTo` 加 `.catch()` 兜底 | 现有 `try { fb.goTo() } catch` 抓不到 async 错误（见 12.5） |

修完后预期首屏 **约 1.1 MB / 约 1 秒**（B 档实测 1.2 秒）。

### 12.5 跳转入口与「点了没反应」

现有 4 个跳转入口，**都没有加载反馈**：

| 入口 | 位置 | 现状 |
|---|---|---|
| 窑口图录点条目 | `goToPage(n)`（`12-bookpage.js:1114`）→ `fb.goTo(want - 1)` | 带动画；库里 `await X(h)` 期间无反馈 |
| 底部进度条拖完松手 | `seekRange` 的 `change` → `goToPage(v)` | 同上；拖动过程中**不预取** |
| 工作台点「示意区」 | `fb.goTo(HINT_PAGE, {instant:true})`（:737） | instant |
| 预览首次打开 | `fb.goTo(1, {instant:true})`（:2115） | instant |

`goToPage` 里的 `try { fb.goTo(...) } catch (e) {}` **拦不住异步失败**
（`fb.goTo` 返回 Promise），页加载失败时表现就是「点了没反应」→ 由第 5 项修掉。

预取的实现：`new Image()` + `await decode/onload`，走 **HTTP 缓存**
（线上 CDN 带缓存头，库里随后的 `fetch` 会命中）。
